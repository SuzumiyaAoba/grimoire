## まず「メモリー」と呼ぶ範囲を決める

広い意味での**メモリー**は、エージェントが推論や行動をまたいで情報を保持し、後続の処理で利用する状態・情報と、その管理機構である。この資料は特に、モデル呼び出しやセッションを越えて残る長期メモリーを扱う。現在の呼び出しで使う context や一時的な計算状態も広義の記憶に含めて論じられるが、長期メモリーとは別の性質を持つ。

保存ファイルだけでなく、何を記録し、いつ読み出し、誤りをどう直すかも設計に含む。

たとえば「次回も箇条書きで答えてほしい」という発言を考える。この発言の文字列を残すのは**記録**、そこから「箇条書きの回答を好む」という情報を作るのは**抽出・解釈**、次の依頼でその情報を読み出して文体に反映するのが**利用**である。この三つの処理はいずれも別々に失敗しうる。

一つの会話ログを保管しても、モデルにそのログが自動で渡るとは限らない。次の呼び出しで使うには、履歴を context に含めるか、外部から関連箇所を読み戻すか、モデル自体を更新する必要がある。CoALA は通常の言語モデルを呼び出し間で状態を保持しないものとして扱い、エージェント側に状態管理を置く。[P-COALA]

メモリーの品質は「何件保存したか」だけでは決まらない。必要な情報を落とさずに記録できたか、質問に合う記録を見つけたか、古い記録と訂正後の情報を取り違えなかったか、根拠のない推測を事実として使わなかったかを分けて見る。

## 人間の記憶を手がかりにする

心理学・認知科学では、記憶を単一の保管庫ではなく複数の機能・過程からなるものとして研究してきた。たとえば、作業中の情報を一時的に保ち操作する working memory、経験した出来事を想起する episodic memory、一般的な事実や概念を扱う semantic memory、技能や手順に関わる procedural memory という見方がある。[H-BADDELEY] [H-TULVING] [H-SQUIRE]

この区分は、エージェントにどの役割の記憶が必要か考える助けになる。CoALA は既存の認知アーキテクチャを参照し、working memory を当面の状態、episodic memory を過去の経験、semantic memory を世界や自身についての知識、procedural memory を行動に使う規則や手順として言語エージェントに当てはめる。[P-COALA]

**役割で見たメモリー**

|            | 人の記憶での目安      | エージェントでの使い方                |
| ---------- | ------------- | -------------------------- |
| working    | 作業中に保持・操作する情報 | 現在の質問、未完了の作業、直近のツール結果      |
| episodic   | 時間・状況をともなう経験  | いつ何が起き、どの応答や操作があったか        |
| semantic   | 出来事の詳細に依らない知識 | 明示された設定、文書中の事実、用語・関係       |
| procedural | 技能・行動の進め方     | ツール手順、承認済みの手順書、再利用する skill |

この類比には限界がある。人の episodic memory は過去の経験を自分の時間の中で想起する神経認知機能として研究されている。データベースに日時付きログを保存しただけで、エージェントがその出来事を人のように経験・想起したことにはならない。[H-TULVING]

同様に、作業用の変数を「working memory」、プロフィール欄を「semantic memory」と呼んでも、人の脳と同じ容量、学習過程、意識、忘却の性質が生じるわけではない。CoALA は設計を整理する概念枠組みであり、認知の同一性を示す実証ではない。[P-COALA]

人間研究から持ち込んだ比喩は、役割を分けるために使い、実際の保存形式・更新規則・検索機能はシステムとして定義する。特に「忘却曲線」を採用したというだけで、情報の正しさや人間らしい忘れ方が再現できたとは結論しない。[P-MBANK]

## もう一つの地図：どこに保持するか

心理学由来の区分が「何の役に立つ記憶か」を表すのに対し、以下は「どこに、どの形で保持するか」を表す。両方の分類は交差する。同じ嗜好をモデルの重みに学習させることも、外部プロフィールに保存して必要時に prompt へ入れることもできる。

**保持場所・機構の分類**

|                    | 保持されるもの                         | 設計上の性質                            |
| ------------------ | ------------------------------- | --------------------------------- |
| parametric（パラメーター） | 学習済みモデルの重み                      | 推論時に明示検索せず働くが、個別情報の所在・訂正・削除を扱いにくい |
| context（文脈）        | 今回の呼び出しでモデルに渡す入力・履歴             | 直接参照できるが、窓の上限・費用・情報配置の影響を受ける      |
| KV cache           | attention 計算で得た key/value の中間状態 | 同じ系列の次 token 生成などの再計算を減らす実行時状態    |
| external（外部ストア）    | DB、ファイル、検索索引、グラフなど              | 明示的に管理できるが、検索・権限・更新・保守が必要         |

**parametric memory** は、学習によってモデル重みに取り込まれた情報を指す。個々の記憶を一覧で見たり、「この一つだけ」を必ず置き換えたりする用途には向きにくい。モデルの重みが事実を保持しうることと、モデルがその知識を正確に取り出し、出典を説明できることは別である。[P-RAG]

**context** は、現在の推論でモデルに提示する入力である。会話履歴を毎回すべて送り直せば、外部への検索を省ける場合があるが、文脈窓に収まる情報量には限りがある。加えて、長い入力を与えられることは、入力内のあらゆる箇所を同じ精度で利用できることを意味しない。[P-LIM]

**KV cache** は、自己回帰生成の attention が使う中間計算を保持して、後続 token の計算を再利用する仕組みである。サーバーやライブラリが会話をまたいで意図的にキャッシュを保持する場合もあるが、会話内容を意味付きで整理するプロフィールや出来事の記録とは役割が違う。寿命、再利用条件、モデルとの互換性は実装に依存する。[D-HF-KVCACHE]

**external memory** は、モデルの外側にある永続ストアである。元の文章、検索用ベクトル、構造化された主張、イベント、要約、手順などを保持できる。保存しただけでは回答に使われないため、質問に合わせて検索し、選んだ情報を context に渡す処理が要る。

### 中身の形も独立した軸

役割や保管場所とは別に、メモリーの「中身」を記録・要約・プロフィール・経験という形で考えると、何を失いやすいかを見積もりやすい。

| 中身の形            | 保持するもの           | 典型的な注意点                          |
| --------------- | ---------------- | -------------------------------- |
| log（ログ）         | 発話や操作を時系列に記録     | 量が増えると検索ノイズが増える。ログそのものは事実の確定ではない |
| summary（要約）     | 複数の記録から短くまとめた内容  | 細部・例外・否定・出典が要約時に落ちることがある         |
| profile（プロフィール） | 嗜好、設定、属性などの集約    | 仮の推定が固定化したり、古くなったりしうる            |
| experience（経験）  | 状況、行動、結果、フィードバック | 一度の成功・失敗から一般化しすぎることがある           |

一つのログからプロフィールを作ることはできるが、これは単なる形式変換ではなく推論をともなう。MemoryBank は対話ログ、日ごとのイベント要約、プロフィール要約を並行して保持する設計例を示す。一方、同論文が使う時間経過・想起頻度による忘却は、著者自身が簡略化された探索的なモデルと説明している。[P-MBANK]

## RAG と長い context はどう関係するか

**RAG（Retrieval-Augmented Generation）** は、質問に関係する外部資料を検索し、その結果をモデルの入力へ加えて生成する方式である。最初の RAG 論文は、モデルのパラメーターに保持された知識と、検索でアクセスする非パラメトリックな文書索引を組み合わせた。[P-RAG]

したがって RAG は記憶そのものの種類というより、外部情報を読み出して回答に使う経路である。静的な文書にも更新されるユーザー記憶にも適用できる。反対に、外部記憶を持っていても検索を呼び出さなければ、その時の回答に使われない。

長い context に履歴や文書をまとめて入れる方法は、関連情報をあらかじめ絞らずに読ませられる。RAG は検索を通じて必要な範囲を選べる反面、検索漏れや順位付けの誤りを受ける。両者のどちらがよいかは、履歴の長さ、検索の質、モデル、質問の種類、費用などに依存する。

「Lost in the Middle」は、評価した複数のモデルで、答えに必要な情報が長い入力の中央に置かれた場合に、先頭や末尾に置かれた場合より性能が下がることを報告した。これは長い文脈を使う際の検査観点を与えるが、現在の全モデルが常に同じ挙動を示す証明ではない。論文のモデルとタスクの範囲を保って読む。[P-LIM]

運用では両者を組み合わせることもできる。外部ストアから検索して関連資料だけを取り出し、その資料をモデルの context に入れて要約・推論する。ただし、RAG が出典を取得しても、モデルが回答を出典に忠実に結び付ける保証にはならない。取り込みから回答までを分けて評価する必要がある。

## メモリーのライフサイクル

実装では、人の記憶過程をそのまま模倣するのではなく、保存・読み出し・訂正に必要な操作を明示する。CoALA は読み出し、推論、長期記憶への書き込みを分けて整理している。[P-COALA]

以下の五段階は、原論文の機能分類を参考に本調査で整理した設計上の流れである。

**メモリーのライフサイクル**

1. `Encode`

   **Encode — 記録する。** 入力から、保存対象、話者・主体、時刻、出典、権限範囲を決める。引用・仮定・予定・否定・推測を確定した事実と混同しない。
2. `Consolidate`

   **Consolidate — 整理・統合する。** 重複する記録を結び、要約やプロフィール、再利用可能な手順を作る。派生内容から元記録へ戻れるようにし、詳細をどこまで圧縮したかを把握する。
3. `Retrieve`

   **Retrieve — 必要なものを読む。** 質問と目的に応じて語句検索・ベクトル検索・構造化検索などを組み合わせ、権限・時点・出典を考慮して候補を絞る。読み出した根拠を現在の作業状態へ渡す。
4. `Revise`

   **Revise — 訂正する。** 新しい発言が既存情報と食い違う場合、出典と有効時点を見て置換・併存・撤回を決める。旧記録を黙って消さず、必要に応じて過去時点の状態も再現できるようにする。
5. `Forget`

   **Forget — 保持を終える。** 有用度による検索優先度の低下、情報の有効期限、利用者からの削除要求を分ける。索引・キャッシュ・要約などの派生物も更新し、削除後に復活しないか確かめる。

この一連の処理は一方向とは限らない。新しい根拠で要約を作り直したり、誤りの訂正によって派生したプロフィールや手順を再評価したりする。更新規則や時間情報を詳しく扱う必要がある場合は、[知識更新の理論と実装](knowledge-updates.md)を参照する。

**優先度と真偽を分ける。** 古い情報があまり参照されないことは、その内容が偽になったことを意味しない。逆に最近何度も検索されたことも、内容が真である証拠にはならない。検索スコア・再利用価値・出典の確からしさ・有効期限は区別して保持する。順位付けで合成する場合も、それぞれの意味を混同しない。

## エージェント記憶研究から学べること

エージェント研究は、メモリーを保管庫だけでなく、モデルがいつ・何を読み書きするかを含む制御の問題として扱う。ここでは代表的な論文の設計思想と、適用範囲を紹介する。

### CoALA：機能と操作を整理する枠組み

CoALA は言語エージェントを、複数の記憶モジュール、内部記憶や外界に働きかける操作、反復する意思決定手順として整理する。エージェント設計では、必要な記憶の種類に加え、各モジュールへの読み書き権限を決めることを提案する。たとえば現在の会話状態は読み書き可能でも、在庫データや実行手順はモデルに無断で変更させない、といった分離である。[P-COALA]

CoALA の重要な示唆は、保存対象と操作権限を別に設計することだ。特に procedural memory を書き換えることは、事実やエピソードを書き足すより危険で、実行コードの誤りや意図しない操作につながりうると論じている。これは特定システムに必須の構成ではなく、比較や設計のための枠組みである。[P-COALA]

### Generative Agents：ログを振り返り、行動計画へつなぐ

Generative Agents は、エージェントの経験を自然言語の memory stream として記録し、関連度・新しさ・重要度で過去を検索し、複数の記録から高次の reflection を生成して、次の計画に使う。研究の主眼は、仮想の町で個人や集団の行動がどれだけ一貫して見えるかである。[P-GEN]

論文は実験の失敗として、適切な記憶を検索できないことや、記憶にない細部を付け加えることを挙げる。したがって、自然な行動や反省文が生成できることは、過去の事実を正確に保持した証拠ではない。25 人の仮想エージェントとゲーム的な環境での結果を、個人向けアシスタント全般の性能と読み替えない。[P-GEN]

### MemGPT：限られた文脈をページングする

MemGPT はオペレーティングシステムの仮想メモリーを手がかりに、限られた context と外部ストレージの間で情報を読み書きし、呼び出しの制御を行う。文書分析や複数セッションの会話を題材に、モデルが必要に応じて情報をページイン・ページアウトする構成を示す。[P-MGPT]

この考え方は、長い文脈を手動で毎回送り直す代わりに、モデルが必要な情報へアクセスする仕組みを設計するうえで参考になる。一方、仮想メモリーの比喩が提供するのは容量・移送・制御の発想である。取得した文章が真実か、二つの矛盾する主張のどちらを採用すべきかは、別の規則で解決する必要がある。[P-MGPT]

### Reflexion：試行のフィードバックを文章で残す

Reflexion は、モデル重みを更新する代わりに、タスクのフィードバックを言語化した振り返りを episodic memory buffer に残し、次の試行で参照する枠組みである。コード生成、逐次意思決定、言語推論などのタスクで、反省文が次の行動に及ぼす効果を評価した。[P-REFLEX]

これは「失敗の原因と次に試すこと」を外部化する例であり、個人の属性を蓄積するメモリーとは目的が異なる。反省の質は、与えたフィードバックとタスク環境に依存する。文章として保存した自己評価が正確で、別の環境にも移る技能になるとは限らない。[P-REFLEX]

### Voyager：成功判定を経たコードを技能として再利用する

Voyager は Minecraft の環境で、課題、状態、エラーを手掛かりに実行コードを作り、環境からのフィードバックをもとにエージェント側の自己検証機構がタスク完了と判定した場合に skill library へ追加する。コードをベクトル索引から検索し、より複雑な技能から既存の技能を呼び出す。[P-VOYAGER]

この例は手続き記憶が文章のヒントに限らず、実行できるコードにもなりうることを示す。ここでの「検証」は論文中のエージェント自己判定であり、人手レビューや形式検証の保証ではない。コード技能を他の環境で再利用する時は別途テストが要る。論文の結果は Minecraft の API と課題設定に関するものであり、一般業務の自動化で同じ成功率・安全性が得られるとは示していない。[P-VOYAGER]

これらの方式は競争する単一の「記憶形式」ではない。Generative Agents は観察・振り返り・計画、MemGPT は文脈管理、Reflexion はフィードバック利用、Voyager は実行技能の再利用に焦点を置く。必要な記憶の役割と、失敗した際の影響に応じて仕組みを選ぶ。[P-COALA]

## 外部ストア、モデル編集、継続学習の境界

| 方式                 | 何を変えるか               | 向きやすい問い                       | 主な注意点                             |
| ------------------ | -------------------- | ----------------------------- | --------------------------------- |
| 外部ストア              | モデル外の記録・索引・要約        | 「どの出典に基づく最新の情報か」「一人の設定を直したい」  | 取り込みと検索が必要。削除は全派生データへ伝播させる        |
| model editing      | モデル内部のパラメーターや表現      | 「モデルの特定の事実応答を編集できるか」          | 効果・一般化・局所性を評価する。外部の履歴や出典台帳にはならない  |
| continual learning | 新しいデータや課題でモデルを段階的に学習 | 「時間とともにモデルを更新し、技能・知識を適応させるには」 | 旧知識の忘却、干渉、学習コストを追う。個別レコードの訂正とは異なる |

ROME と MEMIT は、Transformer の重みを編集して factual association を変える研究である。ROME は GPT 系の特定モデル・評価課題で効力、一般化、特異性を調べ、MEMIT は GPT-J と GPT-NeoX に対する多数の関連付けの一括更新を検証した。これらの結果は、任意のモデルに対して個人情報を安全に編集・削除できる汎用機能を示すものではない。[P-ROME] [P-MEMIT]

継続学習は、時間とともに変化するデータや課題に合わせてモデルを再学習・微調整する研究領域である。過去の知識を使えなくなる catastrophic forgetting が主要課題の一つであり、保持の評価には新しい課題だけでなく、前の課題での性能も必要になる。[P-CLSURVEY]

実務の境界は次のように整理できる。個人や組織ごとに訂正・出典・アクセス権限・削除を管理したい情報は、外部ストアの方が追跡しやすい。モデル編集や継続学習は応答傾向・一般的能力を更新する選択肢だが、保存した一件を取り消す操作と同一ではない。外部から削除しても、同じ情報がモデルの学習データや重みに入っていれば、重みまで消えたとはいえない。

## 評価では段階ごとに失敗を切り分ける

回答の正しさだけを測ると、どこで誤ったのか分からない。少なくとも書き込み、検索、回答、更新・削除、運用コストを別々に調べる。

| 段階    | 例となる指標・試験                           | 見つけたい誤り              |
| ----- | ----------------------------------- | -------------------- |
| 書き込み  | 抽出の precision / recall、話者・日付・根拠の適合率 | 引用や予定を事実として記録する      |
| 検索    | recall\@k、必要な証拠の回収率、古い記録の混入率        | 別人・別時点・別権限の情報を返す     |
| 回答    | 正答、根拠の支持、unknown の適切さ、誤った断定         | 記録が正しくても回答時に取り違える    |
| 更新・削除 | 訂正後の状態、過去状態の再現、派生データの削除確認           | 古い値が残る、削除情報が再生成される   |
| 実運用   | tokens、呼び出し回数、遅延、同期遅延、障害後の回復        | 検索・統合・再索引を含む総費用の見落とし |

テストには、時間が異なる二つの情報、遅れて届く訂正、複数の値の併存、引用や仮定、答えが記録に存在しない質問、利用者による撤回・削除を含める。人手で作ったテストだけでなく、実際の失敗を匿名化して追加し、回答品質と根拠の追跡可能性を両方見る。

LongMemEval は長い会話履歴に対する 500 問を用い、情報抽出、複数セッション推論、時間推論、知識更新、回答保留を評価する。単一セッションの文書 QA では測りにくい能力を含む一方、ベンチマークの正答率は特定のデータ、回答モデル、採点条件での結果である。個々の保存・検索・回答処理を切り分けるには追加の評価が要る。[P-LME]

ベンチマークのスコアや製品の公開値を比較するときは、データセットの版・分割、質問の範囲、取り込み順、回答モデル、judge、利用可能な token 数、背景処理の完了条件をそろえる。比較の詳しい手順と既存ベンチマークの特徴は[評価方法](../evaluation.md)を参照する。

## 用途に合わせて役割を選ぶ

個人アシスタントでは、明示された好みや設定と、過去の具体的な出来事を分けておくと、訂正や削除を扱いやすい。推測した性格・感情を本人の申告と同じ確度で蓄積しない。

研究支援では、要約だけでなく、原資料の版・該当箇所・そこから導いた主張を結び付ける。研究記録を検索できることと、その記録を真実として採用してよいことは区別する。

業務エージェントでは、現在の作業状態、作業履歴、承認済み手順、業務上の事実を区別する。組織・役割ごとに読み書き権限を決め、コードや手順を自動で書き換える操作には事実の追記と異なる検査を設ける。

以上の用途を、オントロジー・根拠・更新規則と一つの具体例でつないだ設計案は[オントロジーとメモリーの適用例](ontology-memory-applications.md)にまとめる。メモリーや検索システムの実装例は[エージェント記憶システム](../systems/agent-memory.md)も参照する。
